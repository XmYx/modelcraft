# Scripting

ModelCraft embeds [Rhai](https://rhai.rs), a pure-Rust scripting language. A script drives the
same command registry as the app, `modelcraft-cli` and the control channel, reads the scene, and
runs inside a sandbox with limits. This page records the language choice, the model, the sandbox
and what is measured. The function-by-function reference is [scripting-api.md](scripting-api.md),
generated by `cargo xtask script-docs` from the table in `crates/script/src/docs.rs` and the
command registry (a test requires the table to list exactly the functions the engine registers,
and `cargo xtask ci` fails when the generated page is out of date).

```
modelcraft-cli run-script scene.modelcraft stairs.rhai -o out.modelcraft
modelcraft-cli run-script new scatter.rhai -o scatter.modelcraft --time-limit 5
modelcraft-cli run-script scene.modelcraft export.rhai --allow-write exports/ --no-save
```

```rhai
let step_count = 12;
undo_group("Staircase", || {
    for i in 0..step_count {
        let s = add_primitive("cube", "Step " + i);
        scale_to(s, 1.0, 0.1, 0.3);
        move_to(s, 0, 0.2 * i, 0.3 * i);
    }
});
print(`${object_count()} objects`);
```

## Example scripts

`examples/scripts/` has seven original scripts, each run against a real document by a test in CI
(`crates/script/tests/examples.rs`), which also fails when a script has no test:

| Script | Does | Arguments |
|---|---|---|
| `scatter.rhai` | Drops copies of a primitive at seeded random places, as one undo step | `count`, `area`, `seed`, `kind` |
| `batch_export.rhai` | Writes every top-level object to its own file (needs write access) | `dir`, `format` |
| `rename_by_pattern.rhai` | Gives the objects matching a pattern numbered names | `pattern`, `name` |
| `mesh_stats.rhai` | Prints vertices, faces, triangles, area and volume of every mesh | |
| `staircase.rhai` | Builds a parametric staircase as one mesh | `steps`, `rise`, `run`, `width` |
| `distribute_selection.rhai` | Spaces the selected objects evenly along an axis | `axis` |
| `dependency_report.rhai` | Lists what each object's evaluation reads | |

```
modelcraft-cli run-script new examples/scripts/staircase.rhai --arg steps=16 -o stairs.modelcraft
modelcraft-cli run-script scene.modelcraft examples/scripts/batch_export.rhai --allow-write out --arg dir=out --no-save
modelcraft-cli batch-script examples/scripts/rename_by_pattern.rhai a.modelcraft b.modelcraft --out-dir fixed --arg pattern='Cube*'
```

## Why Rhai

The choice was between the two mature pure-Rust embeddable languages whose licences are on the
allowlist: Rhai 1.27 and Rune 0.14.2 (both `MIT OR Apache-2.0`). Both were built and run on the
same machine (release build, `CARGO_BUILD_JOBS=3`), with the same hostile scripts. Rows marked
"not evaluated" are things only Rhai was taken far enough to judge.

| | Rhai 1.27 | Rune 0.14.2 |
|---|---|---|
| Version stability | 1.x | 0.x, breaking changes between minor versions |
| 2 million loop iterations (release build) | 291 ms | 181 ms |
| Endless loop | stopped by the operation limit in 2.5 ms (`set_max_operations`) | stopped by `budget::with` in 16 ms |
| Runaway recursion | stopped at the call-depth limit (81 µs) | stopped by its allocation limit (64 ms) |
| Runaway string and array growth | string and array size limits (nested containers count together) | the allocation limit stops both |
| Memory | no allocator cap: container size limits, an operation limit, and a per-run budget for the geometry the API hands out (see below) | a real allocation limit for the whole VM (`alloc::limit::with`) |
| Command arguments from script values | `rhai::serde` converts a script map straight into `serde_json::Value`, so `Command`'s JSON form is the script form | not evaluated (a bridge to `Command` would have to be written) |
| Closures and function pointers (callbacks, `undo_group`) | built in | built in |
| Errors with a place | every error has line and column, parse and run time | not evaluated beyond compile diagnostics, which have spans |
| Limits a script cannot catch | operation, depth, size and our own limits are not catchable by `try`/`catch` | not evaluated |

Rune is faster, and its allocator limit is a better memory guarantee than anything Rhai offers.
Rhai was chosen because a 1.x API will not churn under the app, because its map and array literals
map one-to-one onto the command registry's JSON (no per-command bindings to write or keep in step),
and because every error carries the file, line and column the script editor needs. The speed
difference does not matter for scripts whose time goes into commands; if scripts ever need the
raw speed or a hard memory cap, Rune is the language to evaluate again.

Dependencies Rhai adds: `rhai`, `rhai_codegen` (proc-macro), `smartstring` (`MPL-2.0+`, which the
house rules allow for unmodified third-party use), `thin-vec`, `ahash`, `once_cell`, `smallvec`,
`num-traits` and their dependencies, all `MIT OR Apache-2.0` except `smartstring` and
`tiny-keccak` (`CC0-1.0`). `cargo xtask licenses` checks them.

## The Scripts window

Scripts menu, or Ctrl+J. The editor colours keywords, the script API's function names, strings,
numbers and comments (the tokenizer is `modelcraft_script::highlight`, UI-free and tested to cover
any text exactly), numbers the lines and marks the line of the last error.

| Key (in the editor) | Does |
|---|---|
| Ctrl+Enter | Run the script |
| Ctrl+Shift+Enter | Run the selection; errors keep the line numbers of the file |
| Ctrl+S | Save the script file |
| Esc | Close the window and return to the viewport |

The Output panel lists `print` and `debug` lines, command warnings and errors as
`file:line:column: message`; an error is a button that moves the cursor to its line. A run happens
on the UI thread and is bounded by the limits below, so a runaway script cannot freeze the window
for more than the time limit; Undo reverts what it did. Unsaved edits are never discarded without
a prompt (New, Open and choosing a file ask first).

**Unsaved text.** The window keeps what you typed. A moment (1.5 s) after the text last changed,
and when the app exits, an unsaved script is written to `<state folder>/modelcraft/recovery/scripts/script-draft.json`
(one file replaced atomically, with the file it belongs to); saving, emptying or discarding the
text removes it. At the next start the text comes back as unsaved changes, on its file when that
still exists (the file itself is untouched until you save), and the window opens with a note.
Texts over 4 MiB are not kept (the status line says so once). The file format and its checks are
`modelcraft_script::draft`; damaged or foreign files are ignored.

**Files.** The scripts folder is `<user data folder>/modelcraft/scripts`. Its `*.rhai` files and
one level of subfolders become the Scripts menu (the first comment line is the tooltip); the
`quick` subfolder becomes the Quick Scripts strip under the tool options; `startup.rhai` runs once
when the app starts. A script run from the window may read the script's folder, the project's
folder and the scripts folder, and write nowhere unless "Allow writing files" is on. Then the
window lists the folders it grants: the project's folder (a `scripts-out` folder inside it when the
project is saved straight into the user's home folder or a filesystem root) and the scripts folder.

## Tools, callbacks and arguments

```rhai
register_tool("Add Row", "Adds a row of cubes", || {
    undo_group("Add Row", || { for i in 0..5 { move_to(add_primitive("cube"), i * 3, 0, 0); } });
});
on_selection_changed(|e| print(`${e.selection.len()} selected`));
```

- **Tools.** `register_tool(label, fn)` registers a menu command; the `Session` lists them
  (`Session::tools`) and runs one by label (`run_tool`). The closure keeps its variables between
  runs. A script that runs again replaces the tools and callbacks it registered before (they
  belong to the script by its name).
- **Callbacks.** `on_selection_changed`, `on_scene_changed`, `on_scene_loaded` and
  `on_frame_changed` (or `on_event(name, fn)`) call `fn(event)`; the event is a map with `event`
  and, where it applies, `selection` or `frame`. The host reports an event with
  `Session::fire`. Callbacks run with a shorter time limit (2 s, `Limits::max_event_time`); one
  that fails three times in a row is switched off and says so in its report. Nothing in the
  script crate calls `fire`: the application decides when events happen. In the app (below) the
  Scripts window's session is the one that hears them.
- **In the app.** Registered tools are listed in the Scripts menu under "Scripted Tools" and run
  as one undoable change; the startup script and a script open in the editor can both register
  tools. The app reports events once per frame, never while a drag or a brush stroke is going on
  (the change is reported when it ends), and what a callback changes itself is not reported
  again, so callbacks cannot trigger themselves. While the timeline plays, `frame_changed` and
  `scene_changed` (which change every drawn frame) are coalesced instead of running per frame:
  one batch per 50 ms carrying the newest frame (`event.skipped` says how many frames it
  stands for), all callbacks of a batch share an 8 ms budget and each is stopped after 25 ms, the
  next batch waits until the last one's cost divided by a 25 % duty has passed, and what was held
  back is delivered once when playback stops. A callback cut short only because the others used
  up the budget is skipped, not counted as a failure. The policy is `PlaybackPolicy` in
  `modelcraft-script` (`EventPacer` is the UI-free part; `Session::fire_within` takes the
  budget).
- **Undo.** What callbacks change never adds undo steps of its own. A callback that answers a
  user step (or an agent's or a script's) is merged into that step, which keeps its name, so one
  Undo takes both back and one Redo returns both. A callback that runs for no step (a selection
  or frame change) makes one "Script callbacks" step for everything the callbacks of that frame
  did. The redo history is held aside while callbacks run, so reacting to an Undo does not make
  Redo impossible. (`Document::fold_undo_since` in the engine does the merging; only scene
  changes merge, a sculpt stroke stays a step of its own.) A scene change by the user, a script or an
  agent all count; a frame change poses the scene, so it also reports a scene change. A callback
  that prints or fails shows in the Output panel.
- **Arguments.** `--arg name=value` on the command line becomes `arg("name", default)` and
  `args()`; `current_file()` is the open project's file.
- **Batch.** `modelcraft-cli batch-script` runs one script over many files, see
  [cli.md](cli.md#scripts).

## Over the control channel

`script.run` runs a script on the open scene from outside: through the window's loopback socket
(`modelcraft-cli call script.run '{"source": "add_primitive(\"cube\")"}'`), through
`modelcraft-cli serve` and `control`, and as the `script` tool of the MCP server (`modelcraft-cli
mcp`, with `--app` for the running window). Parameters: `source` (up to 1 MiB), `name` (what error
messages call it, default `agent.rhai`), `args` (an object of strings, numbers and booleans, read
with `arg(name, default)`).

The reply is `{"ok": true, "result": {...}}` where `result` is the report of the run: `ok`,
`value`, `output` (kind, text, line), `commands`, `operations`, `seconds`, `error` (file, line,
column, message) and `selection` when the script changed it. A script that fails is a successful
reply with `result.ok == false` (the MCP tool marks it as an error and still returns the report);
a malformed request is `{"ok": false, "error": ...}`.

An agent's script is as powerful as the agent already is and no more: it runs with the default
limits, with no file access at all (whatever the user allowed their own scripts), no script
library, and the selection of the window (which the script may change). Its changes are ordinary
commands, so each is an undo step (`undo_group` makes one for the whole script) and the window's
status line says an agent changed the scene. Tools and callbacks it registers are dropped when it
ends. Clients are asked for approval like for any other change (`script.run` is a *Changes*
request), and the channel needs its token like every other method.

## Libraries

A script can share code through Rhai modules kept in the scripts folder:

```rhai
// <scripts folder>/lib/shapes.rhai
export const SIDES = 6;
fn row(n, name) { for i in 0..n { move_to(add_primitive("cube", name + i), i * 2, 0, 0); } }
```

```rhai
import "lib/shapes" as shapes;
shapes::row(shapes::SIDES, "c");
```

- **Where.** The name is a path relative to the scripts folder without the `.rhai` (the suffix may
  be given). Conventionally libraries live in `lib/`, which the Scripts menu skips. In
  `modelcraft-cli run-script` the folder is the script's own, or `--library DIR`; `-e` scripts have
  none unless `--library` is given.
- **Sandbox.** A name is plain names joined by `/` (letters, digits, `_`, `-`, space, inner dots):
  no leading `/`, `..`, hidden names, `\` or `:`. The file must be a regular file of at most 4 MiB
  inside the folder after symbolic links are followed (a link that points out is refused). A
  library runs in the importing script's engine, so it has the same operation, time, depth and
  command limits and the same file permissions, and cannot reach more than the script could. At
  most 8 libraries deep, 64 modules per run; an import cycle is an error naming the chain.
- **Reloading.** Libraries are read again on every run, so edits show at once.
- **Tools and callbacks.** They run after the script ended, so the session keeps the modules a
  script imports at its top level as the namespace of the alias for as long as it lives: a tool
  that calls `shapes::row` works later. Two scripts that import different libraries under the same
  alias share the last one loaded, so name aliases after the library. `cmd` and `global` are the
  engine's and are never replaced.
- **Errors** inside a library read `... (in library lib/shapes)`; limits stay limits.

## Recorded macros

Scripts menu, "Record Macro" (also in the command palette, and the first button of the Scripts
window): from then on the commands the user runs are recorded; stop with the same command and the
macro opens in the Scripts window as an ordinary script. Ctrl+Enter replays it as one undo step.

```rhai
// Macro: Macro 1 (3 commands), recorded in ModelCraft. Edit it freely; it runs as one undo step.
let sel = selection();
undo_group("Macro: Macro 1", || {
    let r1 = cmd::add_primitive(#{ kind: "cube", name: "Box" }).created;
    cmd::set_transform(#{ id: r1[0], transform: #{ ... } });
    cmd::rename(#{ id: r1[0], name: "Crate" });
});
```

- **What is recorded.** Commands that made an undo step, one step each (an `undo_group` a script
  ran is one step), a frame change before a command that follows it, and starting or ending a
  sculpt session. An Undo while recording takes the last step off the record and a Redo puts it
  back, so the macro holds what the user kept. Changes callbacks make are not recorded. At most
  20,000 commands are kept (the window says when it cut), and a macro over 8 MiB is refused.
- **Objects.** Objects the macro created are bound to variables and later commands use them
  (`r1[0]`), so a macro works in any scene. Objects that existed and were selected when recording
  started are `sel[i]`, the i-th object of the selection the macro runs with: the script stops
  with "select N object(s) first" when fewer are selected. Any other object keeps its number and
  the macro's first lines say so.
- **Save as Tool.** The Scripts window's "Save as Tool" writes the editor's text, with the name
  typed beside it, to `Macros/<name>.rhai` in the scripts folder (a Scripts submenu) or, with
  "Quick Scripts strip" checked, to `quick/<name>.rhai`. A file that is not a macro written this
  way is never replaced: the name gets a number.
- **From a file.** `modelcraft-cli macro-script steps.jsonl --name Pair -o pair.rhai` writes a macro
  from one JSON command per line (the format of `run`) or from a crash journal, by replaying the
  commands on an empty scene to learn which objects each creates.
- **Limits.** A `batch` command is written as one command, so ids created inside it stay numbers;
  a very long sculpt stroke (more than 20,000 dabs) is more than a script array may hold and the
  replay stops with a limit error. `modelcraft_script::macros` has the writer, and
  `Document::start_recording` the recorder in the engine.

## The model

- **Everything a script changes is a command.** Every entry of
  `modelcraft_engine::COMMANDS` is a function `cmd::<name>(map)` taking the command's JSON as a
  map (`import` is `cmd::import_file`, because `import` is a Rhai keyword), and
  `run(#{ cmd: "name", ... })` takes the whole command. The functions are generated from the
  registry, so a command added there appears in scripts by itself, and a test requires the two
  lists to be equal. A script's changes are journaled and undoable exactly like the app's.
- **Friendly helpers** wrap the common commands (`add_primitive`, `move_to`, `set_attr`, ...);
  they run the same commands.
- **Queries** read the scene without changing it: objects, attributes, selection, the dependency
  graph (`dependencies`, `dependents`, `graph_edges`), the evaluated mesh of an object or of one
  of its history steps (`evaluate`, `evaluate_step`), and evaluation errors.
- **Meshes** are handles: `Mesh` (read-only, from `evaluate`), `MeshBuilder` (positions and faces
  to a new object) and `PositionEdit` (positions of an object that stores its own mesh). Every
  index is checked and named in its error: `vertex 8 is out of range (there are 8, numbered from
  0)`.
- **Undo grouping.** `undo_group("label", || { ... })` makes everything inside one undo step. If
  the closure fails, its changes are rolled back and nothing is left to redo. `batch` is the same
  thing as a command: a list of commands that run all or none as one step.
- **Selection** belongs to the app, not the document. A run gets the selection in a
  `RunContext` and hands back the changed selection.

## The sandbox

A script has no file or network access and no way to start a process: the engine is built from
Rhai's standard package only, `eval` is switched off, modules load only from the scripts folder (see Libraries), and the functions that touch the
disk (`read_text`, `write_text`, `list_dir`, `file_exists`, `export_scene`, and the `import`
command) check a `Permissions` first. The default grants nothing. A path is made absolute, `..`
is resolved and symbolic links are followed before it is compared with the granted folders, so a
path cannot leave them. A command that names a file is checked too, also inside a `batch`.

`Limits` (defaults in `crates/script/src/limits.rs`):

| Limit | Default | Stops |
|---|---|---|
| Operations | 10,000,000 | endless loops |
| Wall-clock time | 10 s, checked as it runs and before every command | slow commands in a loop, anything the operation limit misses |
| Call depth / expression depth | 24 / 48 | runaway recursion, deeply nested source |
| String bytes (all strings of one container together) | 256 KiB | string doubling |
| Array / map entries (nested ones count) | 20,000 / 2,000 | array growth |
| Time of one event callback | 2 s | slow callbacks |
| Commands per run | 100,000 | command floods |
| Geometry built or copied through mesh handles, per run | 4,000,000 vertices, faces and corners | memory from meshes |
| Output lines | 5,000 | console floods |
| File size read or written | 4 MiB | |

Limits a script hits end it with a `Limit` error that `try`/`catch` cannot catch. Plain errors
can be caught.

What is measured, and what is not (Linux, test profile of this workspace):

- An endless loop stops at the operation limit in a few milliseconds; a loop that only counts
  stops at the 10 s time limit.
- The worst memory growth found in a hostile script is adding keys to a map in a loop (Rhai does
  not measure a map when a key is assigned, only when it is built by a function): at the default
  limits it grew the process by about 67 MB (integer values) to 153 MB (an array per key) in about
  one second before the operation limit stopped it. That is the figure to read as the memory bound
  of a hostile script; there is no allocator cap, so it is a measurement, not a guarantee.
- Array growth by `push` is measured per call and rejected at 20,000 entries (Rhai re-measures the
  array on every call, so the cap is kept small; bulk geometry stays in mesh handles).
- A single native command that is already running is not interrupted. Commands bound their own
  work (`MAX_RESULT_FACES`, subdivision levels, the polygon limits), and the time limit is
  checked before the next one.
- Scripts run on the thread that calls `Session::run` (the UI thread in the app). The time limit
  is what keeps the window responsive; a script cannot be stopped from outside while it runs.

## Layering

`modelcraft-script` is an L5 crate beside the app, below it in the stack: it depends on
`modelcraft-engine` and Rhai, never on egui. The app and `modelcraft-cli` use it; nothing in the
core depends on it.
